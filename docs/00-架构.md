# 架构

## 一句话

**文件是记忆，会话是 CPU。** 交易员的能力沉淀在 `trader/memory/`，账户事实在
`trader/paper/`，任何会话（飞书、DSH 对话框、定时任务）都是临时执行器。

## 四个角色

```
飞书私聊（交易台）──┐
定时任务（盘前/收盘）├─→ DSH 会话（workspace = codex\ 目录）
行情监控（止损触发）┘         │
                              ├─ skills/a-share-trader      人格、日循环、风险闸门
                              ├─ skills/knowledge-intake    知识 → 假设
                              ├─ skills/paper-trading       下单、对账
                              ├─ ../ashare-db/strategy-lab  回测、选股、报告
                              └─ a-share-market-data        实时行情
                                        │
                                        ▼
                        trader/memory（知识/打法/日志） + trader/paper（账本）
```

## 四层记忆

| 层 | 谁写 | 内容 | 规则 |
|---|---|---|---|
| 事实 | `paper.py` | 账户、持仓、委托、净值 | Agent 不许手改 |
| 知识 | 人类/Agent | 用户原文 + 结构化 | 原文一字不改，带来源 |
| 打法 | Agent（需批准） | 规则卡 + 证据 + 状态 | 新规则先进候选 |
| 日志 | Agent | 每日复盘、错误、教训 | 每日必写，每周合成 |

## 会话模型

- **飞书私聊 = 交易台**：唯一允许执行交易动作的会话；
- **DSH 对话框 = 研发台**：改策略、跑回测、写知识；
- 两者共享 `trader/` 目录，所以换会话不丢状态；
- 群聊只读（避免多会话并发写账本）。

## 数据流（一个交易日）

```
09:15 盘前  → 读 handover/index/account → 扫昨日信号 → 写 plans/今日.md → 飞书卡片
09:30 开盘  → quote 取价 → paper buy（风控闸门）→ orders.jsonl
10:30/11:20/13:30/14:45 → quote 持仓 → 触发止损/止盈 → paper sell
15:05 收盘  → mark --live → nav → check → journal/今日.md → handover 更新 → 飞书复盘
每周一      → 读 5 篇 journal → 出提案卡 → 人类批准 → 改 playbook
```

## 与 strategy-lab 的关系

- strategy-lab 负责**过去**：规则 → 回测 → 证据；
- 本仓库负责**现在**：证据 → 纸面交易 → 记录；
- 两者的桥：`playbook` 卡引用 `runs/<id>`，回测结论决定打法状态。

## 为什么不用数据库/向量库

条目数量级是几十到几百，`index.md` + grep + 文件读起来最可靠：
可读、可 diff、可 git 审计、Agent 不需要额外工具。等超过 500 条再考虑检索层。
